DepWatch: bản chất luồng theo dõi thay đổi API và thư viện

Tài liệu này giải thích hệ thống DepWatch hiện tại đang hoạt động như thế nào: API chỉ quản lý dữ liệu và lập lịch, RabbitMQ nối các bước xử lý, còn Fetcher, Diffing và Notifier Worker xử lý pipeline nền.

API contract/spec monitoring OpenAPI/Swagger RabbitMQ pipeline SQL Server + MinIO ASP.NET Core + Workers

Mục Lục

1. Tóm tắt bản chất 2. Thành phần hệ thống 3. Luồng tổng quan 4. Dữ liệu lưu trong DB 5. Luồng chi tiết từng bước 6. Theo dõi API OpenAPI 7. Theo dõi thư viện 8. Khi deploy cần chạy gì 9. Giới hạn hiện tại

1. Tóm Tắt Bản Chất

DepWatch hiện tại là hệ thống theo dõi thay đổi của mô tả API và nguồn phát hành thư viện, không phải hệ thống gọi thử API nghiệp vụ. Với API, hệ thống chủ yếu theo dõi file openapi.json, swagger.json hoặc YAML tương đương. Nó tải spec, lưu snapshot, so sánh bản cũ và bản mới, rồi cảnh báo nếu có thay đổi đáng chú ý.

Câu mô tả ngắn gọn nhất DepWatch gọi GET /openapi.json để đọc hợp đồng API, sau đó diff hợp đồng đó. Nó không gọi POST /orders hay GET /users với body/query thật để kiểm tra runtime.

DepWatch đang làm

  • Theo dõi OpenAPI/Swagger specification.
  • Theo dõi GitHub release mới nhất.
  • Theo dõi latest version từ NuGet, npm, PyPI.
  • Tính hash để biết dữ liệu có đổi hay không.
  • Lưu snapshot vào storage.
  • Tạo diff và gửi digest cảnh báo.

DepWatch chưa phải là

  • Runtime API monitoring.
  • Synthetic API testing.
  • Contract test gọi từng endpoint thật.
  • Công cụ tự quét repo công ty để biết project đang dùng package nào.
  • Công cụ tự biết project đang gọi endpoint nào trong code.

2. Các Thành Phần Chính Của Hệ Thống

Hệ thống không chỉ có một API duy nhất. Khi chạy đầy đủ, nó gồm API web, ba worker nền, database, message broker và object storage.

Thành phần Vai trò Có xử lý job chính không?
DepWatch.API Nhận request từ frontend, quản lý user, target, subscription, dashboard, diff query. Đồng thời chứa Hangfire scheduler để định kỳ tạo lệnh quét. Không xử lý fetch/diff/notify trực tiếp. Nó chỉ lập lịch và publish message.
DepWatch.Worker.Fetcher Nghe queue fetch-requested, tải dữ liệu từ bên ngoài: OpenAPI spec, GitHub release, hoặc registry package. Có. Đây là worker lấy dữ liệu mới.
DepWatch.Worker.Diffing Nghe queue diff-requested, đọc snapshot cũ/mới, phân tích thay đổi và tạo record diff. Có. Đây là worker hiểu dữ liệu thay đổi gì.
DepWatch.Worker.Notifier Nghe queue notify-requested, gom diff theo chu kỳ, chống rollback noise và gửi email digest. Có. Đây là worker báo cho user.
SQL Server Lưu user, target, subscription, version snapshot metadata, diff metadata. Không. Đây là nơi lưu trạng thái nghiệp vụ.
RabbitMQ Nối các bước nền với nhau bằng message queue. Không. Đây là đường truyền job.
MinIO / S3 / Azure Blob Lưu file snapshot vật lý và diff JSON lớn nếu cần. Không. Đây là object storage.
Vai trò của Hangfire Hangfire không trực tiếp chạy Fetcher, Diffing hay Notifier. Hangfire chỉ là đồng hồ trong API, định kỳ gọi scheduler để publish FetchRequestedEvent vào RabbitMQ.

3. Luồng Tổng Quan

Đây là toàn bộ pipeline khi hệ thống vận hành bình thường. Mỗi mũi tên qua RabbitMQ nghĩa là service trước publish message, service sau đang chạy độc lập và consume queue đó.

DB RabbitMQ Storage Process 
User tạo target
  -> DepWatch.API
  -> DB: MonitoredTargets

User subscribe target
  -> DepWatch.API
  -> DB: UserSubscriptions

Hangfire trong DepWatch.API chạy định kỳ
  -> ScanScheduler đọc MonitoredTargets + UserSubscriptions
  -> RabbitMQ: fetch-requested

DepWatch.Worker.Fetcher
  -> tải OpenAPI / GitHub release / package registry
  -> tính hash
  -> nếu hash đổi: upload snapshot vào Storage
  -> DB: ApiVersions
  -> DB: update MonitoredTargets.CurrentHash + LastScannedAt
  -> RabbitMQ: diff-requested

DepWatch.Worker.Diffing
  -> đọc ApiVersions
  -> tải snapshot cũ/mới từ Storage
  -> phân tích thay đổi
  -> DB: ApiDiffs
  -> RabbitMQ: notify-requested

DepWatch.Worker.Notifier
  -> đọc UserSubscriptions + ApiDiffs + Users + MonitoredTargets
  -> gom nhiều thay đổi thành digest
  -> gửi email
  -> DB: update LastNotifiedAt + NotifyHashSnapshot

4. Dữ Liệu Được Lưu Vào Database

SQL Server không lưu toàn bộ file OpenAPI lớn trực tiếp. Database chủ yếu lưu metadata, trạng thái theo dõi và kết quả phân tích. File snapshot được lưu ở object storage.

Bảng Lưu gì? Vai trò trong pipeline
Users Thông tin người dùng: email, display name, password hash... Dùng để xác thực và xác định người nhận cảnh báo.
MonitoredTargets Target đang được theo dõi: URL gốc, URL đã normalize, loại target, visibility, current hash, auth header private, thời điểm quét gần nhất. Là bảng trung tâm của hệ thống theo dõi.
UserSubscriptions User nào đang theo dõi target nào, tần suất quét/cảnh báo, lần thông báo gần nhất và hash snapshot đầu chu kỳ. Quyết định target nào cần quét và user nào sẽ nhận digest.
ApiVersions Metadata của mỗi snapshot đã tải: target, version label, file hash, URL object trong storage, captured time, raw summary nếu có. Lưu lịch sử phiên bản để Diffing Worker biết so sánh bản nào với bản nào.
ApiDiffs Kết quả phân tích giữa hai snapshot: old version, new version, severity, JSON mô tả thay đổi, thời điểm phân tích. Là dữ liệu hiển thị trên UI và đưa vào email digest.
RefreshTokens Refresh token của người dùng. Phục vụ authentication, không trực tiếp thuộc pipeline scan.
SourceRegistry Nguồn registry/changelog chuẩn đã biết như NuGet, npm, PyPI, GitHub. Hỗ trợ Fetcher tìm nguồn changelog hoặc registry chính thống.
SourceCache Cache nguồn changelog đã tìm được. Giảm việc tìm kiếm lại nguồn changelog cho cùng target.

5. Luồng Chi Tiết Từng Bước

1

User tạo target

User nhập OpenAPI URL, GitHub repository hoặc package name/registry URL. API nhận request qua TargetsController và gọi TargetService.CreateAsync.

Service dùng TargetUrlAnalyzer để normalize input và đoán loại target: OpenApi, GitHubRelease, NuGet, Npm hoặc PyPi.

Dữ liệu được lưu vào MonitoredTargets. 

MonitoredTargets
- Id
- NormalizedUrl
- OriginalUrl
- DisplayName
- Type
- Visibility
- CurrentHash
- AuthHeaderEncrypted
- LastScannedAt
- CreatedAt
↓
2

User subscribe target

Target là đối tượng dùng chung toàn hệ thống. Một target có thể có nhiều user subscribe. Khi user subscribe, hệ thống không tạo target mới nếu target đã tồn tại. Nó tạo record liên kết user và target.

Dữ liệu được lưu vào UserSubscriptions. 

UserSubscriptions
- Id
- UserId
- TargetId
- ScanFrequency
- ScanPriority
- LastNotifiedAt
- NotifyHashSnapshot
- CreatedAt
Ý nghĩa deduplication Nếu 1.000 user cùng theo dõi một OpenAPI URL, hệ thống chỉ cần quét URL đó một lần theo chu kỳ dày nhất, sau đó kết quả diff có thể phục vụ tất cả subscriber.
↓
3

Hangfire gọi ScanScheduler

Trong DepWatch.API, Hangfire định kỳ gọi ScanScheduler.EnqueueDueScansAsync(). Scheduler đọc tất cả subscription, gom theo TargetId, rồi chọn tần suất quét dày nhất cho mỗi target.

Ví dụ nếu một user chọn Daily và user khác chọn Weekly cho cùng target, hệ thống chọn Daily để đảm bảo không bỏ sót thay đổi.

Nếu target đến hạn quét, scheduler publish message vào RabbitMQ: fetch-requested. 

FetchRequestedEvent
- TargetId
- TargetType
- NormalizedUrl
- AuthHeaderEncrypted
- CurrentHash
Hangfire dừng ở đây Sau khi message được đưa vào RabbitMQ, Hangfire không xử lý fetch/diff/notify. Các worker độc lập sẽ nhận việc từ queue.
↓
4

Fetcher Worker tải dữ liệu

DepWatch.Worker.Fetcher nghe queue fetch-requested. Khi nhận message, nó chọn handler theo loại target.

TargetType Handler Dữ liệu tải về
OpenApi OpenApiFetchHandler File OpenAPI/Swagger JSON/YAML.
GitHubRelease GitHubReleaseFetchHandler Release mới nhất từ GitHub API.
NuGet, Npm, PyPi PackageRegistryFetchHandler Metadata package từ registry để lấy latest version.

Sau khi tải content, Fetcher tính SHA256 hash và so với CurrentHash trong message.

↓
5

Nếu hash không đổi

Nếu hash mới bằng hash hiện tại, nghĩa là dữ liệu ngoài chưa thay đổi. Hệ thống không tạo version mới, không diff và không notify.

Database chỉ cập nhật LastScannedAt trong MonitoredTargets để scheduler biết target vừa được quét. 

MonitoredTargets.LastScannedAt = now
↓
6

Nếu hash thay đổi

Nếu hash mới khác hash cũ, hệ thống coi đây là một snapshot mới. Fetcher upload content vật lý lên MinIO/S3/Azure Blob. Sau đó tạo record trong ApiVersions. 

ApiVersions
- Id
- TargetId
- VersionLabel
- FileHash
- BlobStorageUrl
- CapturedAt
- RawSummary

Sau đó cập nhật target hiện tại: 

MonitoredTargets.CurrentHash = newHash
MonitoredTargets.LastScannedAt = now

Cuối cùng Fetcher publish message vào RabbitMQ: diff-requested. 

DiffRequestedEvent
- TargetId
- TargetType
- OldVersionId
- NewVersionId
↓
7

Diffing Worker phân tích thay đổi

DepWatch.Worker.Diffing nghe queue diff-requested. Nó đọc metadata version cũ/mới từ ApiVersions, sau đó tải file snapshot từ storage bằng BlobStorageUrl.

Analyzer được chọn theo loại target:

  • OpenApiAnalyzer: parse và diff OpenAPI spec.
  • ChangelogAnalyzer: phân loại release notes GitHub bằng keyword/regex.
  • SemverAnalyzer: so sánh version package theo SemVer.

Kết quả được lưu vào ApiDiffs. 

ApiDiffs
- Id
- TargetId
- OldVersionId
- NewVersionId
- Severity
- ChangesJson
- AnalyzedAt

Sau khi lưu diff, worker publish message vào RabbitMQ: notify-requested. 

NotifyRequestedEvent
- TargetId
- DiffId
- Severity
- TargetType
↓
8

Notifier Worker gom và gửi cảnh báo

DepWatch.Worker.Notifier nghe queue notify-requested. Nó tìm các subscription của target, kiểm tra chu kỳ nhận cảnh báo, rồi lấy các diff trong khoảng từ LastNotifiedAt đến hiện tại.

Worker không gửi từng diff riêng lẻ ngay lập tức. Nó gom nhiều thay đổi trong chu kỳ thành một email digest, giúp giảm nhiễu.

Nếu gửi email thành công, hệ thống cập nhật UserSubscriptions. 

UserSubscriptions.LastNotifiedAt = now
UserSubscriptions.NotifyHashSnapshot = MonitoredTargets.CurrentHash

6. Với API: DepWatch Theo Dõi OpenAPI/Swagger Spec

Đây là điểm rất quan trọng để tránh nhầm lẫn. DepWatch hiện tại theo dõi file mô tả API, không gọi thử từng endpoint nghiệp vụ.

Luồng hiện tại

DepWatch gọi:
GET https://provider.com/openapi.json

Sau đó:
- parse spec
- so sánh spec cũ/mới
- phát hiện breaking change
- cảnh báo user

Không phải luồng hiện tại

DepWatch không gọi:
POST https://provider.com/orders
Body: { ... }

DepWatch không kiểm tra:
- endpoint runtime có sống không
- status code thực tế
- latency thực tế
- business response thực tế

Các thay đổi OpenAPI có thể phát hiện

Loại thay đổi Ví dụ Mức độ thường gặp
Endpoint bị xóa /v1/users biến mất khỏi spec mới. Breaking
Method bị xóa POST /orders không còn tồn tại. Breaking
Parameter mới bắt buộc Thêm query tenantId với required: true. Breaking
Parameter optional thành required region trước optional, nay required. Breaking
Request body field mới required Thêm field customerType bắt buộc trong body. Breaking
Response field đổi type amount đổi từ string sang number. Breaking hoặc Warning tùy chính sách.
Endpoint mới Thêm GET /v2/reports. Safe
Nếu provider không có OpenAPI/Swagger Với thiết kế hiện tại, DepWatch không thể diff cấu trúc API một cách chính xác. Có thể mở rộng theo hướng theo dõi changelog/docs HTML, nhưng độ chính xác sẽ thấp hơn rất nhiều so với OpenAPI spec.
API cần auth thì sao? Auth chỉ cần để tải được file OpenAPI private. Hệ thống hiện có ý tưởng lưu AuthHeaderEncrypted và gắn vào request khi fetch spec. Tuy nhiên phần mã hóa thật hiện vẫn cần hoàn thiện nếu dùng production.
API có body thì sao? Body của endpoint không được gửi đi. Nó chỉ được đọc dưới dạng schema trong OpenAPI. Ví dụ spec nói request body có field name, email, field nào required, type là gì. DepWatch diff schema này, không gửi body thật.

7. Với Thư Viện: DepWatch Theo Dõi Nguồn Phát Hành

Với package như NuGet, npm hoặc PyPI, hệ thống tải metadata từ registry để biết latest version. Nó không tự biết project công ty đang dùng package nào nếu chưa có module import/scan project.

Loại thư viện Nguồn theo dõi Cách phân tích hiện tại
NuGet NuGet registry API Đọc latest version, so SemVer: Major = Breaking, Minor = Warning, Patch = Safe.
npm npm registry API Đọc dist-tags.latest, so SemVer.
PyPI PyPI package API Đọc version mới nhất, so SemVer nếu parse được.
GitHub Release GitHub releases/latest API Lấy changelog Markdown, phân loại keyword: breaking, feature, bugfix.
Giới hạn với bài toán công ty Hệ thống hiện theo dõi target/package được user thêm hoặc subscribe. Nó chưa có lớp CompanyProjects, ProjectDependencies để tự quét repo công ty và biết project nào đang dùng package nào, version nào.

8. Khi Deploy Cần Chạy Những Gì?

Bỏ qua Docker hay không thì vẫn cần hiểu rằng mỗi worker là một process/app riêng. Nếu chỉ chạy DepWatch.API, hệ thống chỉ nhận request và tạo message scan. Không có worker thì message sẽ nằm trong RabbitMQ mà không được xử lý.

Tối thiểu cần chạy

  • DepWatch.API
  • DepWatch.Worker.Fetcher
  • DepWatch.Worker.Diffing
  • DepWatch.Worker.Notifier
  • SQL Server
  • RabbitMQ
  • MinIO hoặc object storage tương đương

Nếu thiếu worker

  • Thiếu Fetcher: không ai tải OpenAPI/package/release.
  • Thiếu Diffing: có snapshot mới nhưng không ai phân tích thay đổi.
  • Thiếu Notifier: có diff nhưng không ai gửi cảnh báo.
DepWatch.API
  -> Hangfire Scheduler
  -> RabbitMQ: fetch-requested

DepWatch.Worker.Fetcher
  -> RabbitMQ: diff-requested

DepWatch.Worker.Diffing
  -> RabbitMQ: notify-requested

DepWatch.Worker.Notifier
  -> Email

9. Giới Hạn Hiện Tại Và Những Điểm Dễ Hiểu Nhầm

1. Không phải runtime API monitoring Hệ thống không gọi thử endpoint thật với method/body/query. Nó theo dõi spec.
2. API không có OpenAPI thì khó theo dõi chính xác Nếu nhà cung cấp không có OpenAPI/Swagger, DepWatch không có nguồn cấu trúc đáng tin để diff endpoint, parameter và response schema.
3. Private OpenAPI auth còn cần hoàn thiện Thiết kế đã có chỗ lưu auth header cho private target, nhưng phần mã hóa secret thật cần được triển khai nếu dùng môi trường production.
4. Chưa tự động biết project công ty đang dùng dependency nào Muốn đạt bài toán company dependency impact tracking, cần thêm module import/scan repo để đọc .csproj, package.json, lockfile, requirements file...
5. Vai trò đúng của hệ thống hiện tại Có thể gọi chính xác là API/Library Change Tracker hoặc API contract/spec change monitoring. Đây là nền tốt để mở rộng thành hệ thống impact analysis cho dự án công ty.

Kết Luận

DepWatch hiện tại có pipeline nền khá rõ: API lập lịch, RabbitMQ nối các bước, Fetcher lấy dữ liệu, Diffing phân tích thay đổi, Notifier gửi cảnh báo. Dữ liệu nghiệp vụ được lưu trong SQL Server, còn file snapshot lớn được lưu ở object storage.

Với API, hệ thống theo dõi tốt nhất khi nhà cung cấp có OpenAPI/Swagger spec. Với thư viện, hệ thống theo dõi nguồn phát hành như registry hoặc GitHub release. Để thành hệ thống theo dõi dependency thực tế trong công ty, bước tiếp theo là bổ sung lớp project inventory và dependency discovery.
